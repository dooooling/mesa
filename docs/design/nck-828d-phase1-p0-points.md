## 2. P0 分级

**分级标准（唯一）**：现场是否用它判断「机床是否正常运转」。凡「缺了它就无法回答机床在不在动/在跑哪个程序」的进 P0；只影响追溯、诊断深度的进 P1；**证据不成立或地址被阻塞的一律不进 P0**。

### 2.1 P0（一期必须，10 个）

| 组 | P0 点 | 为什么必须 |
|---|---|---|
| 运行状态 | **A1** 运行方式、**A2** 程序状态 | 判断「机床处于什么状态」的第一层；A2 是唯一已单独复验的状态量 |
| 程序信息 | **B1** 主程序名、**B3** 当前行号 | 判断「在跑哪个程序、程序是否在推进」；B1 已两次真机验证 |
| 进给与主轴 | **C1** 实际进给率、**C3** 进给倍率、**C4** 主轴实际转速 | 判断「是否在切削、是否被人为降到 0、主轴是否在转」 |
| 坐标与位置 | **D1** 各轴实际位置 | 判断「轴是否在动、动到哪」的唯一直接量 |
| 映射支撑 | **D4** 轴名、**D5** 通道→机床轴分配 | 没有它们，`axis=1..8` 只是序号，位置无法交付现场；`0` 值需按「未分配」解释 |

**P0 的证据现状（这是本清单最重要的一句）**：10 个 P0 中 **3 个 `✅`（A2、B1、D1）**、**7 个 `⚠️`（A1、B3、C1、C3、C4、D4、D5）**、0 个 `❓`、0 个 `❌`。即一期必须项**没有一个落在 80 BAD 上**，但**七成只有历史 GOOD**，必须逐点复验后才能签字。

### 2.2 P1（可延后，9 个）

B2 活动程序名、B4 当前程序块、C2 指令进给率、C5 主轴指令转速、C6 主轴倍率、D2 指令位置、E1 刀具号、F1 驱动对象名、F2 电机温度（按驱动对象）。

理由：① 都是「有更好、没有也能判断运转」的辅助量（如 C2/C5/C6 与实际值成对，缺一个仍可判断）；② B4 是 66 字节文本块，信息密度低且停机为空串；③ F1/F2 只在做驱动侧诊断时需要，且 F2 的语义是**驱动对象**不是机床轴，交付时极易被误读。

### 2.3 不在一期（10 个）

A3、A4、A5、B5、C7、D3、E2、F3、F4（`❌` 目录无定义）+ F5（`❓` 被 80 BAD 阻塞）。

理由：前 9 个**不是「还没采」而是「目录里没有」**，需要新增资源/定义或换数据源，属产品决策而非现场验收；F5 是**地址在真机上为 BAD 且根因未确定**，必须先归因（§5.4）。

## 4. 每个 P0 点的验收方法

### 4.1 通用纪律（先于逐点判据）

1. **采样档**：`interval_ms=1000` × **5 min** 为基线档；需要更低负载时用 `interval_ms=5000` × 5 min 替代档。**两档合计 ≤10 min**，遵守诊断方案 `:440` 的「单次 ≤5 min / 单日 ≤30 min / ≤5 次启停 / 两次运行间隔 ≥30 s」。10 点每轮约 10 个请求，远低于 238 点/轮的既有配置。
2. **新鲜度必须逐行核对**，不得只看 `state=RUNNING`（诊断方案 `:651`：`RUNNING` 只证明驱动回了 Ack）。判据三条同时成立：`quality=GOOD` + `value_origin=CURRENT` + `timestamp_ns` 落在本次运行窗口内（质量调查 `:152-156`）。
3. **时间戳是批次时间**：同一轮所有点共享一个 `timestamp_ns`（诊断方案 `:110-113`），因此「新鲜」按**轮**判断：相邻轮差 ≈ `interval`（±50%），且 `采样时刻 − timestamp_ns ≤ 3×interval`。
4. **判据不是等于历史值**：T2a/T2b 的 `_N_MPF0`、`5`、`0.0` 只用于说明「量级/形态合理」，**禁止**写成「必须等于 `_N_MPF0`/`5`」。程序名、行号、倍率、位置都会随机床状态变化，等值判据必然误判。
5. **原始证据**：每次运行按 `capture-points.ps1:15-31` 的纪律抓「时刻 → 状态 → 完整原始响应 → 事后状态」，**不得只存统计摘要**（质量调查 `:151`）；原始响应文本 + SHA-256 才是权威副本（D1 `:18`：`timestamp_ns` 约 1.8e18，超出 JS 安全整数，解析后的 JSON 会丢精度）。
6. **不得为验收操作机床**：禁止为「看到值变化」而启停程序、切换方式、移动轴、复位报警（诊断方案 `:312`）。「变化」类判据只能用**已经发生**的运行记录，或由现场操作员按生产需要自然产生。

|---|---|---|---|

### 4.3 失败记录与止损

- 每段运行固定写 `run-log.md`：档位 / 点集 / interval / 起止(UTC) / 机床状态 / 结果 / 死亡 detail / GOOD:BAD / 判定 / 下一步（字段沿用诊断方案 `:478`）。
- 失败分四类记录，不得合并：① 质量 BAD（记 `quality_code`，注意断线会被覆盖成 `COMMUNICATION_LOST`，此时样本作废）② 时间戳停滞（记相邻两轮 `timestamp_ns` 原值）③ 值越界或与 HMI 不一致（记原始值 + HMI 读数）④ 端点进入 `RECONNECTING/FAILED`（记 `detail`）。
- **P0 专属止损**：任一 P0 点连续 3 轮 BAD，或该点 `timestamp_ns` 停滞 ≥ `3×interval` → 立即 Stop（避免「状态在跑但数据不动」的假健康）。Stop 后按诊断方案 `:398` 五项复核：HTTP 200/500 + `state=STOPPED` + `desired_running=false` + 驱动进程空 + 到目标 `:102` 无 Established。Stop 最坏可达 ≈75–80 s（`:357`、`:386`），客户端超时须 ≥120 s。
