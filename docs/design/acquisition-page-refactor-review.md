## 评审结论（三项核心决定 + 一条入口约束）

| # | 议题 | 结论 | 落点 |
|---|---|---|---|
| 决定 1 | 运行状态未知时能否保存 | **禁止任何形式的保存，包括「只写配置」**。允许查看与编辑草稿、提供刷新状态入口；加载失败/切换连接不得沿用旧状态；连接中/重连中不得当成已停止。真正执行保存前必须**重新确认**运行状态；但这**不等于并发原子保证**（现有后端限制见 §4.4.4） | §2.4、§4.4.1、§4.4.4、§4.7、§6-2 |
| 决定 2 | 无实际修改时是否放行 | **所有驱动路径统一拦截**：判据基于完整有效配置（不是只比 `point_key`），按钮隐藏之外提交函数也须守卫；**不发 PUT、不发 stop、不发 start** | §2.3、§4.4.2、§4.6、§6-3 |
| 决定 3 | 非 NCK 的「成功」判据 | **补通用回读确认，不降级成「已提交」**：现有 GET 接口比对提交值与回读值 → 一致后更新完整保存基线 → 再按用户选择恢复采集；回读失败或不一致显示「保存结果待核对」，不报成功 | §3.1、§4.4.3、§4.5、§6-4 |
| 入口约束 | 导入入口 | **「声明了导入」不代表产品已实现导入**；入口必须同时满足「驱动声明支持」+「当前产品实现可用」，不能仅凭声明恢复后端仍返回 501 的入口 | §4.1.1、§6-10 |

## 评审摘要

| 维度 | 现状 | 重构后 | 主要风险 |
|---|---|---|---|
| 首屏信息 | 四段状态条 + 常驻表单 + 目录统计 + 逐行成功标签 | 四块：连接/状态、周期、列表、添加入口 | 改动面最大，需分步落地 |
| 点位查找 | 238 行平铺，无搜索无分页 | 搜索 + 问题筛选 + 默认 25 项/页（可选 50、100） | 前端过滤的规模边界（§2.7） |
| 编辑 | 内联表单，列表位置被顶走 | 抽屉 + 稳定 `rowId` + 关闭后回到原位 | 需先有稳定的行视图模型 |
| 保存 | 常驻按钮，成功提示出现两次 | 固定保存区；运行态三态；无修改统一拦截；成功 = 回读一致 | 运行态与成功判据都要改语义（§4.4） |
| 提示 | 常驻说明 + 加载即弹 toast | 按节点出现；成功一次、失败持续、待核对单列 | 现有测试断言需同步调整（只改查询方式，不放宽断言） |

## 一、背景与边界

### 1.1 背景

A 组已完成局部修复，且修复已在 `main`：

但页面本身仍然难用：**信息过多、提示常驻、点位不好找、编辑保存费劲**。本稿只解决**页面信息架构**，不解决契约层面的驱动耦合。

本轮评审已就「运行未知能否保存」「无修改是否放行」「非 NCK 成功判据」三项拍板（见文首结论表），原稿中对应的「待确认」已全部替换为结论。

### 1.2 必须明确声明：本稿不做驱动解耦

> 本稿**不做驱动解耦**。现有 `driver_id` / 协议字段名 / 资源 ID 的专用判断**仍然存在**，本稿**不声称已解耦**，也**不把已有耦合包装成已完成**。
>
> 解耦属 **B 组**（权威准入、身份预览接通、质量码命名空间），另稿设计。

本稿只做一件事：把驱动相关的**判断**留在页面层既有分支里，把**展示**抽成不含驱动判断的通用组件。判断本身没有被消除，只是不再散落在表格、抽屉、搜索、分页里。

### 1.3 架构约束（硬性）

1. **通用组件零特判**：本稿涉及的所有通用组件（表格、抽屉、搜索、分页、草稿、保存区）**不得新增** `driver_id`、协议字段名、资源 ID 特判。判定口径见 §2.8。
2. **校验保护一条不减**：以下守卫在重构后必须原样存在，且仍由页面层/既有模块执行，不下沉到通用组件：

| 守卫 | 现落点 | 重构后 |
|---|---|---|
| 服务端身份预览（Key 唯一来源） | `NckPointFields.tsx:209-290`、`nckCatalog.ts:597-602` | 不变 |
| 输入变更后旧 Key 立即失效 | `NckPointFields.tsx:292-296`、`:197-199` | 不变 |
| 保存前重新核验 | `EndpointAcquisitionPane.tsx:769-779` | 不变 |
| 保存后回读确认（NCK） | `EndpointAcquisitionPane.tsx:835-851` | 不变（并按 §4.4.3 扩展到所有驱动） |
| 完整 Schema 保存守卫 | `descriptorCompatibility.ts:139-155`、`EndpointAcquisitionPane.tsx:739-741` | 不变 |
| 任务快照门 / 不可安全编辑门 / scope 准入门 | `EndpointAcquisitionPane.tsx:731-734`、`:745`、`:747-753` | 不变 |

3. **保存语义不变**：仍是全量快照替换（运行中先 Stop → PUT → 回读 → 按选择恢复），不改后端契约、不改 `PUT /tasks/{endpoint}` 请求体形状。回读是页面层的确认步骤（§4.4.3），不新增后端字段或端点。

#### 1.3.1 本轮新增的页面层约束（叠加在六项守卫之上，不替代任何一项）

| 约束 | 要求 | 落点 |
|---|---|---|
| 运行态未知禁止保存 | 含「只写配置」在内的一切保存；只允许查看/编辑草稿 + 刷新状态 | §4.4.1 |
| 保存前重新确认运行状态 | 点击保存后、任何 stop/PUT/start 之前重新读取；不一致即中止 | §4.4.1 |
| 无实际修改统一拦截 | 所有驱动、按钮与提交函数双层守卫；不发 PUT/stop/start | §4.4.2 |
| 通用回读确认 | 非 NCK 也必须回读比对；不一致不报成功 | §4.4.3 |
| 导入入口双条件 | 驱动声明 **且** 产品实现可用；当前后端 501，不得开放 | §4.1.1 |

> 上述约束都是**页面层**行为，不改变后端契约；其中「保存前复核」只降低用过期状态决策的概率，**不提供并发原子保证**（§4.4.4）。

### 1.4 六项固定范围（不扩大）

| # | 范围 | 本稿对应章节 |
|---|---|---|

## 二、结果 1：默认页面布局

### 2.1 布局原则

- **一屏四块**：连接与运行状态、采集周期、点位列表、添加入口。除此之外默认不出现第五块。
- **默认安静**：成功、正常、已保存都是默认态，不占视觉；只有**需要动作**的信息才出现（真实问题照常出现，见 §3.3）。
- **位置稳定**：任何编辑动作都不把用户从当前页/当前行带走。
- **保存区可多条件可见**：不是只由「有修改」驱动（§4.7）。
- 线框为示意，列宽可调；`⋯` 表示行内「更多」。

- 运行状态**无法确认**时，保存按钮禁用，保存区改为「运行状态未知，无法保存 ［刷新状态］」；**草稿仍可编辑**（§4.4.1）。没有修改时保存区仍不出现，只在顶部状态行提示「状态未知」。

### 2.6 点位辨识规则（统一口径）

原稿 §2.6（允许标识补充摘要）与 §2.9（标识只属于技术详情）互相矛盾，现统一为下列规则：

1. **行 = 当前可编辑单元**：NCK 为「一个点位」，非 NCK 为「一条资源选择（可含多个输出）」。两者共用行组件，但**不声称是同一模型**。
2. **名称**：优先 Descriptor / 定义目录的 `label`（中文优先，`nckPointModel.ts:39-45`），缺失退回 `variable_id` / `resource_id` / 「原生点位」。**不得按地址编造业务名**（沿用 `nckPointDisplay.ts:1-12`、`:121-144` 的硬约束）。
3. **名称不足时允许展示必要标识**：当名称是「原生点位」这类通用名，或同页出现重名时，行内**必须**补可区分标识（地址摘要或 `point_key` 尾段）。标识不是技术详情的专属物。
4. **地址摘要优先「字段标签 + 值」**：原生地址显示为「区域 C · 区域号 1 · 模块 122 · 列 5 · 行 1」这类带标签形态。标签优先取 Schema 的 `label`；NCK 原生字段当前 label 是英文（`drivers/sinumerik-nck/src/lib.rs:199-246`），展示层用字段名翻译表给出中文（与 `nckPointDisplay.ts:38-42` 的 `TARGET_LABELS` 同一机制），表里没有的字段用 Schema label 或字段 key。**只翻译字段名，不猜业务名**；**不得**只显示无说明的 `C / 1 / 122 / 5 / 1`（现状 `:64-69` 正是该形态，需改）。
5. **语义点位**沿用 `pointSummary` 的「标签 值」摘要（`pointSummary.ts:127-137`、`nckPointDisplay.ts:72-110`）。
6. **不得留空**：没有任何可读参数时回退 `point_key`（`pointSummary.ts:136`）。
7. **两行即可判定**：任意两行在同一页内必须能靠「名称 + 摘要」区分；做不到时摘要补 `point_key` 尾段。
8. **技术详情仍是完整信息的唯一位置**：完整 `point_key`、原始参数 JSON、定义版本、身份来源放在技术详情（`EndpointAcquisitionPane.tsx:1349-1373`）；行内只放**必要**标识，不放完整 JSON。

### 2.7 搜索 / 筛选 / 分页规则

| 能力 | 规则 |
|---|---|
| 搜索 | 匹配 **标题、地址/摘要、标识**（`point_key` / `variable_id` / `resource_id`）三段，包含匹配、大小写不敏感；输入即过滤 |

|---|---|---|---|
| 名称 | 1 行 | 1 行 | 1 行 |
| 摘要 | 1 行（标签 + 值，含地址） | 1 行（标签 + 值，含地址） | 1 行（标签 + 值，含地址） |

| 保存成功 | 回读一致后 | **只出现一次**简短通知（保存区结果行），同时清除未保存标记、保存区收起 |
| **配置已保存但启动失败** | 回读一致、启动步骤失败 | 保存区转为结果态：**清除草稿标记**，保留「重试启动」「查看诊断」；**重试只调用启动步骤** |

| 实际读取异常 | 已获得真实运行结果时 | 采集页只在点位行显示问题标记；明细统一在「数据」页，避免各页重复报警 |
| 页面级加载失败 / 配置损坏 | 加载完成且确认失败时 | 页面内一条说明影响 + 动作：「配置加载失败，暂时无法编辑。［重试］」；**不得因为「首屏 Alert 数为 0」而隐藏**（§3.3） |

### 3.2 两条原则

- **正常信息默认安静，异常信息直接关联处理动作。** 「已保存」「校验通过」「格式正确」都是默认态，不占视觉；出现的信息必须能点、能定位、能继续。
- **用户还没有输入或提交时，不先摆出一屏错误。** 未选变量不渲染字段错误（沿用 `NckPointFields.tsx:307-309`、`:362-364`）；抽屉未打开时页面无字段级错误。

### 3.3 真实问题不能隐藏（首屏安静只适用于正常场景）

「首屏 Alert 数为 0」**只适用于正常场景**（加载成功、配置完整、身份核验通过）。加载失败、已有配置损坏、必需的身份检查失败等**真实问题照常出现**，不得被验收指标隐藏：

- 用一句话说明**影响**与**下一步**（「配置加载失败，暂时无法编辑。［重试］」）；
- **必需的身份检查失败**要展示**可处理的原因**：正文写「哪些点位、哪一步失败、用户可以做什么」，**原始错误码/响应放进技术详情**（现状 `EndpointAcquisitionPane.tsx:1207-1232` 把 `status.code` 直接摆在正文，需分层）；
- 保留原始错误码与响应，供排查时展开（`EndpointAcquisitionPane.tsx:1481-1495` 的 `issues` 原样展示是正确形态，保留）；
- **无需默认解释**快照、接口路径、内部错误码——这些只在技术详情里出现。

### 4.4 保存

| 当前情况 | 保存区动作 | 说明 |
|---|---|---|
| 已停止 | 「保存配置」 | 保存后保持停止，不自动启动（沿用 `deviceModel.ts:481-485`） |
| 运行中（含连接中/重连中过渡态），选择恢复运行（**默认**） | 「保存并恢复采集」 | 停止 → 写入 → 回读 → 启动 |
| 运行中，选择保持停止 | 「保存并停止采集」 | **次级选项**，默认不选，不弹二次确认 |
| **运行状态无法确认**（加载失败/切换连接/刷新失败/Endpoint 不在清单） | **禁止任何保存（含只写配置）**，只显示「刷新状态」 | 不得推断「已停止」；**允许查看与编辑草稿** |
| **没有实际修改** | 不发 PUT、不发 stop、不发 start；不显示成功 | 所有驱动路径统一拦截（§4.4.2） |
| **保存结果待核对** | 先「重新核对」，不得直接重新 PUT | 回读失败或不一致（§4.4.3） |
| **配置已保存但启动失败** | 「重试启动」 | 只重试启动步骤，不重复整套保存 |

运行状态未知时，即使没有修改，也必须在顶部状态行给出「状态未知」与刷新入口；保存区只在「有修改 / 正在保存 / 结果待核对 / 恢复失败」时出现（§4.7）。

执行顺序与结果落点沿用现有生命周期状态机（`deviceModel.ts:474-494`、`LifecycleOutcome:462-467`），保存区只负责**展示**它给出的 outcome，不自行解释。

不为正常保存增加多层确认弹窗：运行中的「会中断」说明本身就是确认，按钮文案即动作。

#### 4.4.1 保存前重新确认运行状态（决定 1 的追加要求）

打开页面时的运行态只用于渲染；**真正执行保存前必须重新确认一次**，避免用户长时间编辑后仍依赖打开页面时的旧状态：

- 在点击保存后、**任何 stop / PUT / start 之前**重新读取（现有 `GET /api/v1/endpoints`，`api.ts:115`；现状只在加载时读一次 `EndpointAcquisitionPane.tsx:537-542`，`save()` 直接使用闭包里的 `running`，`:814-815`）；
- 复核结果与界面显示一致 ⇒ 按原路径执行；
- 不一致 ⇒ **中止本次保存**，以新状态为准更新界面、动作与文案（不得沿用旧状态），由用户**再次点击保存**后才执行——不额外弹确认框（与「不为正常保存增加多层确认」一致）；
- 读取失败 / Endpoint 不在清单 ⇒ 判定为**运行状态未知** ⇒ **禁止保存**（含只写配置），显示「刷新状态」；草稿保留；
- 切换连接时 `running` 必须立即复位为「未知」，不得沿用上一个连接的值（现状复位块 `:433-456` 未复位 `running`；`listEndpoints` 的 catch `:552-556` 也未复位）。

#### 4.4.2 无实际修改：所有驱动路径统一拦截（决定 2）

- **判据基于完整有效配置**，不是只比 `point_key`：NCK 用合并后的任务集逐字比较（`endpointSavePlan.ts:180-186`、`:202-208`）；非 NCK 同样用 `sameTaskSet`（`:142`、`:202-208`）。前端草稿指纹（`acquisitionDraft.ts:3-13`、`:29-35`）只用于展示与行标记，不单独作为拦截判据，避免两套口径。
- **拦截层**：按钮可见性只是体验，**提交函数也必须有守卫**。落点：`planEndpointTaskSave` 是唯一决策点（`endpointSavePlan.ts:97-109`），非 NCK 的 `changed` 从「仅信息性」（`:75-77`、`:137-143`）改为**强制拦截**（与 NCK 的 `NO_CHANGES` 同口径）；`save()` 在 `:793-800` 统一处理；`canApply`（`:1460-1472`）共用同一判定。
- **效果**：不发 PUT、不发 stop、不发 start；提示为 info「未检测到实际修改」（`:797` 已是 info，保持不变，不得改成 success）。
- **覆盖**：所有驱动路径，包括非 NCK；只切换「保存后保持停止/恢复采集」不算修改（该选项不进任务集）。
- **不改** merge 逻辑与 `preservedTasks` 的逐字保留。

#### 4.4.3 非 NCK 成功判据：通用回读确认（决定 3）

成功 = **回读一致**，不是「PUT 返回 2xx」，也不降级成「已提交」。步骤固定：

1. **比对**：用现有 GET 接口（`readBackTasks` `EndpointAcquisitionPane.tsx:141` → `GET /api/v1/tasks?endpoint=`，`crates/core-api/src/lib.rs:2327-2333`）读取回读值，与**本次提交的配置**比对。**所有路径统一确认「完整提交配置」** —— 含**采集周期**、**每个点位的完整参数**、以及**保留任务**（不被本次编辑覆盖的其他任务）。**只比点位会漏掉「点位相同、周期未保存」的情形**；既有 `samePoints`（`endpointSavePlan.ts:215-218`）与 `sameTaskSet` 都需按此口径对齐，不得只比点位。
2. **更新基线**：一致后才刷新**完整任务基线**（`setSavedBaseline` `:854-858`）—— 必须同步更新周期、点位参数与保留任务的完整基线，**不能只更新展示计数或点位列表**；不得在 PUT 2xx 时就刷新。
3. **恢复采集**：再按用户选择执行启动（`:877-886`）。

失败处理：

- 回读请求失败，或回读值与提交值不一致 ⇒ 显示「**保存结果待核对**」，**不报告成功**，不刷新基线；
- 待核对期间主操作只能是「重新核对」（再次 GET 比对），**不得直接重新 PUT**；核对确认未写入后，才允许用户主动「重新保存」（重新走完整保存前检查）；
- 核对一致 ⇒ 更新基线，并**继续执行用户选择的恢复采集**（原保存可能停在写入后、启动前）；启动失败则进入「已保存但启动失败」，只重试启动；
- 比对按逐字相等，**不设归一化豁免**（若服务端对 `schedule` 等字段有合法归一化，必须先在实施中确认并显式列出，未确认前一律按不一致处理）。

> 现状差距：回读函数注释明写「仅 NCK 使用」（`:134-140`），非 NCK 路径「明示不做回读」（`endpointSavePlan.ts:75-77`）。本稿把回读提升为**所有驱动**的通用成功判据。

#### 4.4.4 边界：这不是并发原子保证（现有后端限制必须明确写出）

保存前复核**不等于**原子保证。以下限制是现状事实，本稿不消除、也不假装已消除：

| 限制 | 现状证据 |
|---|---|
| PUT 是**全量替换**，不接受期望版本/条件写 | `crates/core-api/src/lib.rs:2406-2425`；请求体与请求头都没有 `If-Match` / 期望 `revision` |
| GET 虽返回 `revision`，但**没有条件写入口**，revision 不能用于乐观锁 | `:2327-2333`（返回 `revision`）与 `:2371-2426`（PUT 不校验） |
| 后端只在请求到达时检查「是否运行中」，不检查任务集是否被别人改过 | `:2406-2413`（运行中直接 409 `CONFLICT`） |
| stop → PUT → start 是**三次独立请求**，不是事务 | `EndpointAcquisitionPane.tsx:814-886`、`deviceModel.ts:474-494` |
| 打开页面时读取的任务快照会被长时间复用；期间的第三方改动会被本次全量快照覆盖 | 快照只在加载时读取 `:460-536`；`preservedTasks` 由该快照拼装 |

因此本稿只保证两件事：**前端不会在运行状态未知时发出请求**、**回读不一致不报告成功**。它**不保证**两个客户端同时编辑时的结果正确性。要获得原子保证，需要后端支持条件写/版本号（属后端契约变更，另立项，不在本稿）。

#### 4.4.5 中断说明不写时长（对应评审规则 2）

原稿「约 1–2 秒无新数据」**删除**：该数字没有跨驱动的测量依据（不同驱动、不同点位数、不同连接方式的中断时长不同）。统一写：**「保存会暂时中断当前连接的采集」**，不承诺时长；实际恢复时间以运行结果为准。

### 4.5 失败恢复

| 问题 | 面向用户的提示与操作 |
|---|---|
| 参数未填写 | 「请填写通道编号」，显示在字段旁，不弹窗 |
| 点位重复 | 「这个点位已经存在」，提供「查看已有项」 |
| 已有配置不能通过校验 | 「3 个点位需要处理」，提供筛选和编辑 |
| 保存前检查失败 | **自动定位第一个问题，不先停止采集** |
| 运行状态复核失败或已变化 | 「运行状态已变化或无法确认，本次保存未执行」+「刷新状态」；**不发任何请求** |
| 无实际修改 | 「未检测到实际修改」，不发请求（info，不是成功） |
| 停止失败 | 「未能停止采集，已取消本次保存」，可重试（沿用 `deviceModel.ts:486-487`） |
| 写入后无法确认结果（回读失败/不一致） | 「**保存结果待核对**」+「重新核对」；不得直接重新 PUT，不报告成功（沿用 `EndpointAcquisitionPane.tsx:838-850` 的回读失败分支并升级为持久状态） |
| 保存成功但启动失败 | 「配置已保存，但恢复采集失败」+「重试启动」/「查看诊断」（沿用 `:910-913`）；**重试只调用启动，不重复整套保存** |

### 4.6 关键规则

1. **错误详情保留原始代码与响应**，供排查时展开；面向用户的一行文案不暴露内部码（身份核验失败也按此分层，§3.3）。
2. **保存失败时保留草稿**：点位、周期、变更计数都不清空（现有 `saveIssues` 已原样保留，`EndpointAcquisitionPane.tsx:810`、`:866`）。
3. **配置已确认保存后（写入 + 回读一致），即使恢复运行失败，也不能继续显示成「配置尚未保存」**：基线必须在回读一致后才刷新（`:854-858` 已是该口径），启动失败只影响「运行状态」这一项。
4. **成功提示只在确认完成时出现一次**：保留保存区结果（`ApplyWithRestart.tsx:69-92`），删除 toast（`:891`、`:897`）；失败也改为保存区**持续展示**，不用一次性 toast（`:903`、`:907`、`:912`）。
5. **无实际修改统一拦截**（§4.4.2）：按钮与提交函数双层，所有驱动。
6. **成功判据统一为回读一致**（§4.4.3）：NCK 与非 NCK 同一口径。
7. **运行状态未知禁止保存**（§4.4.1）：含只写配置；草稿仍可编辑。
8. **启动失败只重试启动**（§4.5）：不 stop、不 PUT。
9. **行标记与撤销按 §4.8**：稳定 `rowId`、新增后移除抵消、恢复原值取消标记。

### 4.7 保存区状态机

| 状态 | 进入条件 | 展示 | 退出 |
|---|---|---|---|
| 隐藏 | 无修改，且无进行中/待核对/恢复失败 | 不占空间（页面底部无条） | 出现第一处修改 / 进入待核对 / 启动失败 |
| 待保存 | 有修改、未保存 | 变更摘要 + 放弃修改 + 保存按钮（运行中含中断说明） | 保存 / 放弃 / 撤销全部修改 |
| 保存中 | 点击保存（含状态复核） | 按钮 loading + 步骤文案；输入与抽屉动作禁用 | 完成 / 失败 / 待核对 |
| 保存失败 | 停止、写入或回读任一步失败 | 错误条 + 下一步动作；草稿与行标记保留 | 重试 / 放弃 / 重新核对 |
| **结果待核对** | 回读失败或回读不一致 | **持续展示**「保存结果待核对」+「重新核对」；**不显示成功、不发 PUT** | 核对一致 → 更新基线并按选择恢复采集（启动失败则进入「已保存但启动失败」）；核对确认未写入 → 保存失败 |
| 已保存（启动成功/无需启动） | 回读一致，且启动成功或本就不需要启动 | 一次简短成功，清除未保存标记，随后收起 | 自动 |
| **已保存但启动失败** | 回读一致，启动步骤失败 | 结果态：**清除草稿标记**，只保留「重试启动」「查看诊断」「关闭」；不再显示变更摘要与「放弃修改」 | 重试启动成功 / 用户关闭 / 产生新修改（回到待保存，并保留「上次保存后采集未恢复 ［重试启动］」入口） |
| 状态未知 | 运行态无法确认（含加载失败、切换连接、刷新失败、Endpoint 不在清单） | 禁用保存 + 「刷新状态」；草稿可编辑 | 刷新成功（转为已停止/运行中）；切换连接后仍为未知，不沿用旧值 |

补充：

- **「有修改 / 正在保存 / 结果待核对 / 恢复采集失败」任一成立，保存区就不得隐藏**（规则 1）。
- 保存中禁止关闭抽屉或切换连接（避免「请求还在飞、页面已换」的错位）；失败后不自动重试，也不循环重试。
- 「配置已保存但启动失败」时清除草稿标记（行标记、计数、摘要），但**保留处理入口**：保存区不收起，转为结果态。

### 4.8 行标识与撤销规则

| 项 | 要求 |
|---|---|
| `rowId` 生成 | 页面层在加载快照/新增行时分配一次，之后不随内容变化；删除后不回收、不复用 |
| 禁止 | 数组下标（现状 `EndpointAcquisitionPane.tsx:1294` 用 `${point_key}-${idx}`、`:1418` 用 `idx`）；可变的 `point_key`（编辑会改 key；非 NCK 同一资源多输出时 key 由输出决定） |
| 编辑 / 搜索 / 分页 | `rowId` 保持不变；排序、过滤只改变可见集合，不重新分配 |
| 新增后移除 | **抵消**：草稿回到新增前状态，不产生「移除」计数，摘要不出现「新增 1 · 移除 1」 |
| 修改后恢复原值 | **取消标记**：按完整有效配置比对（`acquisitionDraft.ts:29-35`、`endpointSavePlan.ts:202-208`），不是「改过就标记」 |
| 删除后重新添加 | 分配**新 `rowId`**（仅用于界面定位），但**若最终有效配置及顺序与基线一致 ⇒ 变更计数归零、保存区收起、不发请求**。`rowId` **不参与配置差异判定** —— 变更判定只比有效配置与顺序 |
| 摘要措辞 | 写成「**3 项点位变更；周期另有修改**」这类分栏表述，避免「3 项修改」把周期也算进去的歧义 |

### 5.4 验收不通过的典型信号

出现以下任一现象即判**不通过**，不进入下一轮评审：

- 首屏出现任何绿色「校验通过」标签；
- 238 行同时存在于 DOM（未分页）；
- 编辑并确认后回到第 1 页，或滚动位置被重置；
- 保存失败后草稿计数归零，或行标记消失；
- 保存失败后只留一条会消失的 toast，没有可点击的处理位置；
- 同一次保存出现两条成功提示；
- PUT 请求发出时 `changed === false`；
- 运行状态未知（加载失败/切换连接/Endpoint 不在清单）时仍发出 PUT/stop/start；
- 非 NCK 未回读就报告「已保存」，或回读不一致仍显示成功；
- 「保存结果待核对」状态下直接重新 PUT；
- 启动失败后重新执行 stop/PUT（重复整套保存）；
- 保存区在「正在保存 / 结果待核对 / 恢复采集失败」时被隐藏；
- 「首屏 Alert 数为 0」的判定掩盖了加载失败或配置损坏。

## 六、与现有实现的差异与冲突

| # | 设计条目 | 现状 | 冲突性质 | 处理建议 |
|---|---|---|---|---|
| 1 | 抽屉 + 分页 + 位置保持 | 无分页、无抽屉，表单常驻（`EndpointAcquisitionPane.tsx:1152-1182`、`:1251-1378`） | **结构性冲突**，改动量最大 | 先抽 `PointRow` 视图模型（含 `rowId`），再换容器；分页与抽屉可分两步 |
