**"不允许重试"的准确含义（三句，不得只引其中一句）**：

1. **人工不主动重试**：不点第二次 Start、不"再试一次看看"、不自动进入下一轮（§7 统一流程、§10.4）。
2. **异常时立即 Stop**（§7 任一触发即停）。
3. **但"不允许重试"≠"不会重连"**：Stop 生效前 Core 仍可能发起重连——`RECONNECT_BACKOFF_SECS = [1, 2, 5, 10, 30]`（`crates/driver-manager/src/endpoint.rs:48`）**只对"连续失败且从未进入 `RUNNING`"的尝试递增**；一旦某次尝试短暂进入 `RUNNING`，退避下标归零（`endpoint.rs:59`、`:416-417`），实测节奏约 **3.58 s/次且可无限持续**（诊断方案 `:610-614`、`:643`）。因此"不允许重试"只约束**人**，**不构成"Stop 后不会再有连接"的保证**；判据必须包含 **Stop 后核验无新的 `epoch` 变化、无 `RECONNECTING`**（§5.3-⑥），否则判为**未停干净**。

**变更控制**：冻结表内任一项变更（含"只多读 1 点""5000 改 4000""只延长 10 秒"）都使本申请**立即失效**，须重新编制、重过 §4、重新裁决；执行中发现配置与本文档不符 ⇒ 按 §7-S6 立即 Stop。

### 4.6 第六道执行前门（G6）：watchdog **就绪（ARMED）**；**T0 在 FIRED 时由 watchdog 自行生成**

> **一句话**：**watchdog 未就绪（未 ARMED），不得 Start。** 没有独立看门机制，30 秒截止就只是"希望主流程走到那一步"，不构成执行安全。

**为什么必须拆两阶段（消除 T0 悖论）**：G6 过去要求"Start 之前就提交实际的 `T0+30 s` 截止时间"，而 `T0` 又被定义为 watchdog 真正发出 Start 的时刻——**Start 尚未发出时实际 `T0` 还不存在**，两项不能同时成立。因此 G6 拆为 **ARMED（就绪，Start 前判定）** 与 **FIRED（实际启动，Start 后发生）**：

| 阶段 | 含义 | 判定时点 | 需要什么 |
|---|---|---|---|
| **G6-ARMED（就绪）** | 看门机制已武装：脚本存在、自检通过、独占 Start 与截止 Stop 的调度权、不依赖被测流程 | **Start 之前** | **不需要 T0**，只需证明"已就绪且能自主计时" |
| **G6-FIRED（实际启动）** | watchdog 已发出 Start，并由 **watchdog 自己**记录 `T0` 与截止时刻 | **Start 之后**（执行中的事件） | `T0` 由 watchdog 在发出 Start 的同一时刻**自行写入**日志 |

- **门禁只看 ARMED**：G6 的通过条件 = 下表 **ARMED 全部满足**。**FIRED 是执行中的事件，不是前置门**；它未发生（Start 未发出）⇒ 本轮根本没有开始（无采集、无 PASS），按 §10 记原因，**不按"门未过"记**。
- **人工不得预先填写 `T0` 或截止时间**：二者**只能**由 watchdog 在 FIRED 时刻生成（写入 `t0.stamp` 与 `run-log.md`）。§10.2 签字栏**不得**出现任何具体 `T0`/截止时刻，签字只确认"记录机制"。
- **截止时刻 = watchdog 自己记录的 `T0 + 30 s`**，**不接受**外部（人工、主流程、抓证脚本）指定或修正。

**G6-ARMED 判据（全部满足；Start 之前判定）**：

| # | 就绪判据 | 证据 |
|---|---|---|
| G6-ARMED-1 | watchdog 已作为**独立进程**启动，PID 与启动时刻记入 `run-log.md` | 进程列表 + `run-log.md` |
| G6-ARMED-2 | **自主计时已武装**：截止偏移 **30 s 以常量固化在脚本内**，脚本具备"发出 Start 的同一步骤取 `T0` → 写入 `t0.stamp`/`run-log.md` → 到点发 Stop"的完整路径；**不需要**任何外部传入的 `T0` 或截止值 | 脚本原文（含 30 s 常量与取时刻位置）+ `t0.stamp` **本轮尚不存在**（Start 前不应生成） |

#### 4.6.1 离线故障模拟（**G6-ARMED-5 的通过条件之一；离线进行，不连真实机床**）

> **目的**：证明"**Stop 的发出不依赖任何 HTTP 请求完成**"。**全部用本地假端点**（`http://127.0.0.1:<port>` 的桩服务）**或不可达地址**；watchdog 以 `-BaseUrl`（或等价参数）指向它。**不得**用 `192.168.15.60:102` 做任何模拟，**不得**启动真实驱动，**不得**连接机床。模拟中的 `T0` 同样由 watchdog 自行生成（与正式执行同一代码路径），人工不预填。

| # | 模拟场景 | 做法 | 必须验证什么 |
|---|---|---|---|
| M1 | **同步请求阻塞** | 假端点让 `GET /endpoints/{id}` 挂起 **N ≥ 35 s**；模拟时把**观测请求超时放宽到 N 或取消**（生产仍用 `-TimeoutSec 5`），以证明**不靠 HTTP 超时兜底** | Stop **仍在 `T0+30 s` 发出**（记录实际发出时刻与偏差）；观测线程卡住**不推迟** Stop |
| M2 | **Start 请求超时** | 假端点对 `POST .../start` 不响应或超时（≥10 s） | watchdog **不等待** Start 返回，仍按 `T0+30 s` 发 Stop；退出码与日志完整 |
| M3 | **端点无响应** | `-BaseUrl` 指向不可达地址（如 `http://127.0.0.1:1`） | watchdog **不静默退出**：仍执行停止流程（发出 Stop 尝试、记录失败原因），退出码非 0 并打印处置提示 |

- **每份模拟记录必须含**：`T0`（watchdog 自记）、Stop 实际发出时刻、偏差、退出码、`watchdog-states.jsonl`（可只有失败行）。偏差 **≤ 1 s** 视为调度未被阻塞；**> 1 s 即 G6-ARMED 不通过（NO-GO）**，不得以"实际也停了"放行。
- **M1 的阻塞时间必须长于 30 s**：若观测请求在模拟中因 5 s 超时提前返回，则**未构成**"同步阻塞"验证，**不得**记为通过（那只是超时兜底，不是解耦证明）。
- **模拟通过 ≠ 真机通过**：它只证明**调度解耦**，不证明机床会停——真机停止时刻仍由 §5.3 六项判据另行观测。

**纪律**：

- **自检纪律**：G6-ARMED-4 **只能**在 Start 之前做（此时端点本已 `STOPPED`，Stop 幂等且不改配置）；**不得**在 Start 之后用自检代替真 Stop，也不得用自检制造"已验证"的错觉。

- watchdog 的**实现要点**见 §5.1；**Start/Stop 竞态处理**见 §5.3 与 §4.7。

### 5.1 窗口定义

| 项 | 值 |
|---|---|
| 计划开始 / 结束（本地时间） | **待填** / **待填**（结束须含 Stop 与恢复，留 ≥5 min 余量） |
| `interval_ms` | `5000` |
| 运行观察窗口 / 截止 | **≤30 秒**（硬上限）；截止 = **watchdog 自记的 `T0` + 30 s**，到点由 **watchdog 无条件**发 Stop（**不等主流程、不等抓证完成**；§4.6、§5.3）。**该 30 s 是"Stop 指令发出时刻"的保证，不是"设备已停止"的保证**（§5.3） |
| 计时起点 `T0` | watchdog **发出 Start 请求的同一时刻**、以**自身单调时钟**记录的本地时刻（**含建连时间**，不因"还没 RUNNING"而延后截止）；**只能由 watchdog 在 FIRED 时生成**，人工/主流程/抓证脚本**不得预先填写或修正**；Start 是否返回、何时返回都不影响截止 |

**watchdog 实现要点（独立进程，与主流程解耦）**——本文件**不创建**脚本，执行前须按下列要点落地并经监护人按 §4.6 逐项核对：

1. **独立进程**：`pwsh -File stop-watchdog.ps1`，独立于抓证进程与执行人的操作节奏；**不 import 驱动/Core 代码、不读其内部循环、不以端点状态决定"何时该 Stop"**。支持 `-BaseUrl`/`-EndpointId` 参数：正式执行指向真实 Core，§4.6.1 离线模拟指向本地假端点/不可达地址。
2. **计时源与 T0 生成**：自身 `[System.Diagnostics.Stopwatch]` 单调时钟；`T0` = 发出 Start 请求的**同一时刻**（先取时刻、紧接发出请求，两者之间不得插入其它等待），**由 watchdog 在 FIRED 时自行写入** `t0.stamp`/`run-log.md`；**不采用**服务端时间，也**不接受**主流程/人工传入的 `T0` 或截止值（**人工不得预先填写**）。
3. **职责**：watchdog **独占** Start 与截止 Stop。Start 用 `Invoke-WebRequest -TimeoutSec 10`，**只发一次、不重发**；超时/异常只记录，**不阻塞** 30 s 计时。
4. **截止动作**：到达 `T0+30 s` **立即**发 `POST .../stop`（`-TimeoutSec 120`），**不等待** Start 响应、**不等待** `capture-points.ps1`（其本就不启停端点，`capture-points.ps1:1`）。**Stop 的发出不依赖任何 HTTP 请求完成**。
5. **观测**：每 **200 ms** `GET /api/v1/endpoints/{id}`（`-TimeoutSec 5`），逐行追加 `watchdog-states.jsonl`（`t_local`、`t_unix_ns`、`state`、`desired_running`、`epoch`、`detail`、`http_status`），覆盖 `T0-2 s` 至最终 `STOPPED` 后 **10 s**；总上限 **120 s**。**观测必须运行在独立执行流**，其阻塞/失败/超时不得影响计时与 Stop。（`T0-2 s` 是**事后相对标注**：观测先启动，`T0` 生成后再折算相对时刻，**不代表**观测启动时已知 `T0`。）
6. **双向解耦（硬性）**：**计时与 Stop 的调度**放独立 runspace/job/线程，**与状态观测解耦**——观测卡住不得推迟 Stop；同时 **Stop 请求**也放独立 runspace/job 发出，主循环继续采样——**Stop 可能挂 75–80 s 以上**（§5.3），观测不能跟着卡住。两个方向都不得互相阻塞，且已由 §4.6.1 的 M1–M3 离线验证。
7. **退出**：判据（§5.3-⑥）满足 ⇒ 退出码 0；120 s 仍未满足 ⇒ 退出码非 0 并打印隔离流程（§5.3 处置 ②–⑤），由监护人执行。

### 5.3 Stop 时间约束（**本轮最关键的一条，不得改写**）

> **30 秒是"停止指令的发出时刻保证"，不是"物理停止保证"，也不是"Stop 完成时间"。** watchdog 在 `T0+30 s` 无条件发出 Stop，不依赖主流程是否走到那一步；但**watchdog 能按时发出 Stop ≠ 设备读取在 30 秒时立即结束**——Core 的 Stop 路径仍可能有长时间等待（**典型 75–80 s，尾部无界**，见下），**实际停止时刻必须由"停干净"六项判据另行观测**。**不得**把 30 秒写成"30 秒内一定停住"或"30 秒后设备已安全"。

- **Stop 完成时间：典型最坏 ≈75–80 秒，但这不是严格上界**（诊断方案 `:357`、`:386`）：teardown 小计 ≈35 s（post 5 s + terminate 5+5 s + reader 5 s + drain 15 s，`:375-383`）+ **取消覆盖不到的**建连/配置闭环 ≈46 s（`DRIVER_STARTUP_TIMEOUT` 6 s + 4 个 RPC × 10 s，`:384`）。**该估算不含"强杀后等待子进程回收"的无界时间**：`DriverProcess::terminate` 的宽限只包住第一次 `child.wait()`（`crates/driver-manager/src/process.rs:122`），**强杀后的第二次 `child.wait()` 没有 timeout**（`process.rs:127`）；`terminate_after_shutdown` 同样（`:144`、`:153`）。因此 **75–80 s 只能写作"典型最坏估计"，不得作为超时判据、不得当作安全承诺**。
- **客户端超时 ≥120 s 只是"客户端愿意等"**（诊断方案 `:351`），**不等于服务端保证 120 s 内停住**；HTTP 层无全局超时，Stop 会挂到 teardown 结束（`:386`）。**"≥120 s" 是等待上限，不是完成保证。**
- **超过 120 s 仍未 `STOPPED` ⇒ 按隔离流程处理，不再等**：① 阻断出站（防火墙 Block `192.168.15.60:102`，对机床零风险，诊断方案 `:405`）→ ② 杀驱动进程（`:404`，会触发重连，故**必须先阻断**）→ ③ 杀 mesad（`:406`，须先确认 `desired_running=false`）→ ④ **物理隔离只拔测试主机网线**，不得擅自断产线交换机口（`:407` 的 E4 会影响整线）；**每一步后复核状态**（`state`/`desired_running`/驱动进程/到 `:102` 的连接），全过程记入 §10.3。
- **三条硬性纪律（逐字保留，第 1 条已指向 watchdog）**：
  1. **到达运行截止时间必须立即发出 Stop（由 watchdog 无条件发出），不得为了等 `prestop` 快照而延长采集。**
  2. **提前触发停止条件时，立即执行停止流程**（§7），不等到截止时间。
  3. **Stop 未能及时完成时，由现场人员按批准的安全处置流程处理，不得假定远程 Stop 必然即时生效。**
- **Start/Stop 并发竞态（必须按此处理，不得假设"先 Start 后 Stop"的顺序成立）**：
  - **机制**：Stop 在 `manager.is_running()` 为假时**直接置 `desired_running=false` 并返回 200**（`core-api:2169-2175`）；若 Start 随后才走成功路径，它会把 `desired_running` **重新置 true**（`core-api:2153-2156`）⇒ 端点可能在 **Stop 之后**才进入 `RUNNING`。这不是 Stop 失败，是**竞态**。
  - **Start 超时/未返回时，watchdog 仍必须按截止时间发 Stop**——截止与 Start 的返回值无关（§5.1-3/4）。
  - **在途 Start 规则（硬性）**：① **执行前**：存在**遗留的在途 Start**（请求已发出、未收到明确结果）⇒ **禁止现场执行**（§4.7-G7-3）。② **执行中**：watchdog 按设计**不等** Start 响应（§5.1-3/4），因此 Start 结果在截止前可能仍"在途"——此时**不得**把"Start 已发出"当作"已安全进入采集"，采集得以继续的唯一理由是**截止 Stop 已由独立执行流调度**，**不是**因为 Start 已确认成功。③ **裁决时** Start 仍无明确结果 ⇒ **不得判 PASS**，按竞态记录（`RACE_START_AFTER_STOP`），本轮不计 PASS。
  - **性质与责任**：该竞态是 **Core 生命周期缺陷**，本文档的处置只能**兜底发现并收敛**，**不能证明它已消除**；**执行前必须由独立代码修复解决**（§4.7-G7），本文档不替代修复。
  - Stop 发出后**继续观测**：若看到 `RUNNING` 或 `epoch` 变化 ⇒ **再次 Stop**（最多 3 次），并在 `run-log.md` 记 `RACE_START_AFTER_STOP`（含两次 Stop 的时刻与完整状态序列）。
  - **判据以"最终观测到 `STOPPED` + `desired_running=false`"为准**，**不是**"Stop 请求已发出"。
- **"停干净"六项判据（缺一不算）**：① HTTP 200/500（`core-api:2181-2190`）② `state=STOPPED` ③ `desired_running=false` ④ 驱动进程空 ⑤ 到 `192.168.15.60:102` 无 Established（`:398`）⑥ **自首次观测到 `STOPPED` 起连续 10 s（≥10 次、1 s/次）内 `epoch` 不再变化且未出现 `RECONNECTING`**（§3.5）。**看到 500 不等于没停住**（drain 失败也 500，但 `desired_running` 仍落 false，`:396`）；**看到 200 也不等于停干净**（竞态可让 Start 迟到生效）。

### 5.4 冷却与总量

单次 ≤5 min、单日累计 ≤30 min、**≤5 次启停**、两次运行间隔 **≥30 s**（等旧连接彻底关闭）——全部出自诊断方案 `:440`。本轮实际 ≤30 s + 1 次启停，远低于上限。**超窗**（计划结束仍未恢复完成）⇒ 本轮作废，记 NO-GO/INVALID，**不得**"延长窗口再跑一次"。

### 9.3 判定分级

| 判定 | 条件 |
|---|---|
| **PASS** | §9.1 **九条**全满足 |
| **PASS-WITH-NOTES** | §9.1 **九条全满足**，且只存在**不影响结论的说明项**（如 HMI 无对应显示、值语义待确认）。**"说明项"仅限"证据已完整、结论不受影响"**；**不得**用它放行任何证据缺失、观测中断或判据不明的情形；**日志缺失不属于说明项**（见下方判定口径） |
| **FAIL** | 出现 §7 触发，或 §9.1 第 1–6 条任一不满足 |
| **INVALID** | 证据缺失（§6 不全）、**G6-ARMED 未就绪或观测中断（无法持续观测端点状态）**、Stop 未确认停干净（六项缺一）、恢复未完成/对账不一致、或执行偏离冻结项 |

**判定口径（与 §6.3 一致，不得两说）**：

- **日志缺失不是 NOTES，也不是 INVALID，且不进入判定分级**：进程日志本就不是判据（§6.3）；**可选的进程日志缺失不影响 PASS，也不单独产生 NOTES**——它是既定环境事实（§2.1-③），不属于 PASS-WITH-NOTES 的"说明项"。它缺失只说明"少一份旁证"，不影响 §9.1 的任一条。
- **"没看到错误"不是证据**：没有状态序列就没有"停干净"的结论；没有原始快照就没有"4/4 GOOD"的结论。
- **观测能力红线**：watchdog 不能持续观测端点状态 ⇒ **INVALID**，且**不得启动**（§4.6）；已启动则立即 Stop。

**INVALID ≠ FAIL**：INVALID 说明"这轮什么也没证明"，**不得**用于任何结论，也不得"挑好的数据留下"。
